# Phase 12 Readiness Report

**Run date:** 2026-10-28  
**Scope:** Browser-to-backend verification, deployment readiness, and integration stabilization

## Outcome

The previous shared-browser registration attempt did not complete and was not a passing test. Inspection identified a concrete configuration mismatch: the guarded test backend listens on port `3011`, while `client/src/api.js` defaults to `http://localhost:3000/api`; no frontend test API override had been set. The previous browser trace was not retained, so this is a confirmed configuration defect consistent with the earlier timeout, but cannot be proven as its sole cause. The new Playwright configuration sets `VITE_API_BASE_URL=http://localhost:3011/api`.

The automated browser run also exposed a test-harness issue: hard page navigations reset the app's intentionally memory-only authentication state. The browser test now navigates through React Router links (and uses in-app history navigation for the other-tenant deep-link check). The complete run passed.

## Storage and deployment readiness

- The current document service stores files privately under `server/private/uploads/fdr` by default, or under `FDR_STORAGE_DIR`. It validates file signatures, generates random storage keys, limits upload size, verifies checksums, and downloads only after authorization.
- The current adapter is a local filesystem adapter. No persistent volume, private object-storage adapter, or deployment target is configured or verified. If the chosen host has an ephemeral filesystem, deployment is **blocked** until a persistent private volume or private storage adapter is configured and tested. Do not place the directory in a public static root.
- The frontend requires `VITE_API_BASE_URL` at build time for the production backend URL. No production URL was supplied; the verified build used the development default and does not certify a production deployment.
- The backend default port is `3000`; `npm start` runs `node src/server.js`. Set production `PORT` and `FRONTEND_ORIGIN` to the actual host values, and allow only the production frontend origin.
- Atlas access should allow the backend's required egress only. The actual Atlas allowlist was not inspected because no deployment host/network was specified. Use a least-privilege application database user for the production database and a separate least-privilege account/database for tests; avoid broad public IP allowlists.
- Keep MongoDB, Sarvam and JWT credentials in the backend deployment secret manager. Never expose them through `VITE_*`, frontend code, logs, or reports. Rotation status for credentials previously shared in conversation remains unverified.
- Use a newly generated, high-entropy `JWT_SECRET` of at least 32 characters. Browser tokens are memory-only and do not persist across refresh.
- The database health endpoint is `/api/health`; the isolated database check passed. The endpoint reports database connection state rather than a production deployment health certification.
- Maturity reminders remain disabled by default. The scheduler is in-process; do not enable independent schedulers on multiple production instances without coordination.

No production deployment was attempted. Production readiness is not established by the successful build or local E2E results.

## Exact local synthetic demo commands

1. Copy `server/.env.example` to `server/.env`, provide a non-production MongoDB URI, generate a fresh JWT secret, and leave reminder scheduling disabled. Do not copy production credentials or real FDR documents.
2. In one terminal:

   ```powershell
   cd server
   npm install
   npm run db:check
   npm run bootstrap:admin
   npm start
   ```

3. In a second terminal, set the API URL to the local backend and start the frontend:

   ```powershell
   cd client
   npm install
   $env:VITE_API_BASE_URL = "http://localhost:3000/api"
   npm run dev
   ```

4. Open `http://localhost:5173`, register a synthetic institution, submit only generated synthetic FDR data/documents, and use separately provisioned synthetic reviewer credentials. For browser E2E verification, use the isolated `server/.env.test` setup and commands in the root README instead.
